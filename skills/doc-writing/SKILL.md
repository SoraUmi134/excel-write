# 人に渡す文書を作る

調べ物の結果を、チームで判断に使う文書にするときの決まり。
読む人は、調べた過程を見ていない。文書だけで話が通じるように書く。

## 書く前に決めること

1. **読む人と使い道。** 誰が読んで、何を決めるのに使うのか。例: 「Capability だけに寄せる案を、チームで採るか決める」。
2. **結論を 1〜2 文で。** 文書の冒頭に置く文。ここが決まらないうちは書き始めない。
3. **置き場所。** 関係する資料（Excel など）と同じフォルダに置き、互いに名前で触れる。人のフォルダに置く前に、同じ役目の文書が無いか探す。

## 書き方の決まり

- **日本語のふだんの言葉で書く。** 略号や道具の名前は、初めて出るときに一言添える。内部の呼び名や番号を主語にしない。文の組み立ては explain-before-shorten の skill に従う。
- **結論から書く。** 冒頭に結論と、作った日付、対象の版（例: GSD 1.20.0 時点）。版が進むと中身が変わる話は、必ず版を書く。
- **話の筋ごとに見出しを分ける。** 1 つの見出しに 1 つの主張。根拠はその下に箇条書きで並べる。
- **箇条書きの 1 項目は「リンク ＋ 何が書いてあるか 1〜2 文」。** リンクだけを並べない。読む人が開かなくても要点が分かるようにする。
- **実測と、文書に書いてあることを分ける。** 自分で試して分かったことは「実測（日付・版・条件）」と書く。文書の記述は引用元をリンクする。推測は推測と書く。
- **末尾に「読む時の要点」。** どの節が芯で、どの節が補足かを 2〜3 文で。

## 根拠のリンク

- **該当の一文へ飛ぶリンクにする。** 見出しがあれば `#見出しの id`、無ければ `#:~:text=該当の一文`（ブラウザがその文を探して色を付ける）。GitHub の issue のコメントは `#issuecomment-番号`。
- **今の版の文面で確かめてから使う。** 手元の古い写しで探した文が、今の main には無いことがある。`gh api -H 'Accept: application/vnd.github.raw' repos/持ち主/名前/contents/パス` で今の文面を取り、文があるかを grep する。
- **`#:~:text=` には記号の無い一続きの文を選ぶ。** GitHub の markdown は、太字の `**` や `コード` の記号が消えた状態で照合される。日本語や空白は URL 用に変換する（空白は `%20`）。
- **行番号で指さない。** 版が進むとずれる。どうしても書くときは「行番号は版で動く」と添える。
- **保守者の判断はコメントそのものへ。** issue 全体ではなく、決めたコメントへリンクし、日付を書く。

## Excel の図に入れる文

- 図に入れるのは**ラベルと番号と短い注意だけ**。手順の長文や説明は、図の外（文書）に書く。
- 注意は「問題点N」の吹き出しに、主語のある文で 2〜3 文。最後に参考リンクの札。
- 既存の図の文の調子（字体・色・言い回し）に合わせる。描き方は excel-figure の skill。

## 人のファイルを直すとき

- 直す前に、前に読んだときから変わっていないか確かめる。変わっていたら、その版を土台にする。
- 直す前に控えを取る。控えの場所は報告に書く。
- 頼まれた所以外は変えない。直した後、変わったのが狙った部分だけかを比べて確かめる。

## 渡す前の見直し

- 冒頭の結論だけ読んで、話が通じるか。
- 初めて出る略号・道具の名前に説明があるか。
- 日付と版が書いてあるか。実測と文書の記述が混ざっていないか。
- リンクが該当の文へ飛ぶか（少なくとも数本は実際に開いて確かめる）。開いて確かめていないリンクがあれば、そう書く。
- 個人情報（氏名・電話番号・メールアドレス）や秘密の値（API キーなど）が入っていないか。
